# 本地化日记式记账软件 PRD

## 1. 产品目标

用户只需用接近日记的自然语言描述一笔消费或资金变化，系统负责提取、计算并组织可统计的账目信息，避免用户在记录前先手工完成金额计算、分类和备注整理。

目标平台为 iPhone 和 Android。两端共享同一套产品语义与账本合同，不能因平台不同产生不同的记账、解析或统计口径；一期采用 Expo / React Native + TypeScript，完整技术边界以 `docs/TECHNICAL-SELECTION.md` 为准。

### 1.1 第一期范围

- 单设备、单人、单账本。
- 支持自然语言记账、本地结构化账目、模式默认标签和本地统计。
- 支持语音辅助录入：App 按 sherpa-onnx 官方推荐使用 SenseVoiceSmall INT8 + Silero VAD 在设备端模拟流式识别；停顿后展示已完成语段的转写预览，用户松手后冲刷尾段并把最终文字合入原文；用户仍需点「记下来」才提交。
- 支持按时间范围和所选业务字段把本地账本导出为 Excel 工作簿，也可以一键导出全部时间、全部业务字段的完整账本，供其他软件或人员继续分析。
- 不实现设备同步、账户体系、家庭成员、共享权限或家庭汇总。
- 不实现从 Excel 导入或用 Excel 完整恢复 App 内部状态；分析导出与备份恢复是两个不同能力。
- 不为尚未实现的同步和家庭能力保留可运行的兼容分支或双轨数据路径。

### 1.2 后续目标

- 同一个人可以在 iPhone 与 Android 之间同步同一本个人账本。
- 多个个人账本可以按家庭汇总。
- 个人账本仍是个人记录的事实源，家庭汇总不能取代或改写个人账本。
- 每条个人记录需要有明确的家庭纳入状态；未纳入家庭的记录不得出现在家庭成员可见的数据或家庭统计中。
- 家庭汇总应引用被纳入的个人记录，不能复制出一份独立、可能与个人账本发生漂移的账目事实。

首要目标：

- 支持一次原始输入解析为一条或多条并列消费记录；每条消费记录只表达一笔消费，不包含子消费明细。
- 支持行程、地点等持续上下文，后续记录可以自动继承，无需重复输入。
- 支持用户开启带有默认标签的记账模式，在一段时间内快速复用旅行等上下文。
- 支持类目、行程、地点、商户、渠道等多维统计，不把所有信息压缩到单一层级分类中。
- 区分本次实付、优惠券抵扣和消费归属。
- 永久保留用户原始输入，使结构化结果可以修正或重新解析。

## 2. 本地数据与在线解析边界

- 第一期完整账本只保存在用户自己的设备上，本地账本是唯一正式数据源。
- 允许联网调用 AI，把用户提交的自然语言转换为待确认的结构化结果。
- 在线 AI 只承担单次解析，不保存或管理账本状态，也不能成为历史记录、当前上下文或统计结果的事实源。
- 发送给 AI 的内容应限制为完成本次解析所必需的原文与相关上下文，不上传完整账本。
- 为了归一标签，可以向 AI 提供本地已经使用的相关标签名称、类型与别名；不得因此上传包含这些标签的历史账目明细。
- AI 返回结果必须先写回本地记录，统计功能只读取本地确认后的结构化数据。
- 无网络或解析失败时，用户原文仍然立即保存在本地，并明确标记为“待解析”；不得阻止用户继续记录，也不得静默猜测结构化字段。
- 用户可以在本地修正解析结果，并保留原始输入与修正后的最终结果。

### 2.0 一期 AI 接入：个人 BYOK（自备密钥）

一期产品是**个人、单设备、用户自备密钥（BYOK）**应用。客户端直接调用用户配置的**一个** OpenAI 兼容 Chat Completions 提供商（例如 DeepSeek），**不**部署 Cloudflare AI 网关，也**不**在应用包内或仓库中内置供应商密钥。

#### 2.0.1 分层与正式真相（架构合同）

| 层                              | 职责                                   | 是否正式真相               |
| ------------------------------- | -------------------------------------- | -------------------------- |
| SQLite 账本                     | 原文、作业、已生效扁平消费记录         | **是** — 唯一账本事实源    |
| 应用状态机                      | 提交原子性、整体校验、入账/待确认/失败 | **是** — 唯一可入账路径    |
| 安全配置库（expo-secure-store） | 用户 Endpoint / API Key / Model        | 配置真相，**不是**账本事实 |
| AI 提供商响应                   | 候选结构化结果                         | **否** — 不可信提案        |
| 统计 / 导出 / UI 状态           | 投影与表现                             | **否**                     |

- Provider 输出永远是不可信提案；仅本地整表 schema/领域校验与现有应用状态机可使记录生效。
- 禁止静默部分入账、禁止合成 fallback 记录、禁止把密钥或完整账本写入日志/导出/SQLite。

#### 2.0.2 配置合同

- 同一时间仅一份**生效**提供商配置：OpenAI 兼容 Chat Completions 配置文件，字段为 **Base URL（Endpoint）**、**API Key**、**Model**。
- 不实现提供商注册表、多 provider fallback、自动 model fallback、网关 fallback 或兼容别名双轨。
- API Key 由用户在 App 内输入，**仅**存入 `expo-secure-store`；不得写入 SQLite、日志、导出、仓库文件、超过编辑表单所需时长的 React 状态，或错误文案。
- Endpoint 与 Model 可与 Key 同属同一安全配置仓储，以保证原子读写与简单语义。
- 设置界面必须提供：Endpoint、API Key、Model、保存、测试连接/解析（明确提示会产生小额计费请求）、密钥已配置时的掩码展示、以及破坏性清空。
- 尚未保存提供商配置时，表单默认填入 DeepSeek 推荐值：Endpoint 为 `https://api.deepseek.com`，Model 为 `deepseek-v4-flash`；用户仍可自由修改，默认值不得覆盖已保存配置。
- 已保存且有效的配置应消除“缺少 AI 配置”类警告；缺失或已清空配置时解析作业显式失败，**不丢失**作业行。
- 必须向用户简短披露：root/越狱设备仍可能暴露本地密钥。

#### 2.0.3 Base URL 归一化（保存时一次）

保存时按下列**唯一**约定归一化 Endpoint，非法则拒绝保存：

1. 去掉首尾空白。
2. 去掉末尾 `/`（可重复去掉至不再以 `/` 结尾）。
3. 必须是可解析的绝对 URL（含 scheme 与 host）。
4. 真实远程主机必须使用 **HTTPS**；仅本地开发环回主机（`localhost`、`127.0.0.1`、`[::1]`）允许 HTTP。
5. **不**静默改写用户路径（例如不自动追加或删除 `/v1`）；用户需按提供商文档填写（DeepSeek 默认示例：`https://api.deepseek.com`）。

#### 2.0.4 配置变更与作业

- 设置变更**显式**作用于之后可执行的待处理/未来解析作业；已生效消费记录永不因改配置而改写。
- 作业可持久化非密钥执行元数据供诊断：provider origin/host、model、config revision；**永不**持久化 API Key。
- 前台与后台任务必须解析同一安全配置；启动/回到前台续跑可执行作业。

#### 2.0.5 调用与校验

- 使用官方 OpenAI JS/TS SDK（`apps/mobile` 直接依赖、精确版本），以 `baseURL` + `apiKey` 配置。
- 使用提供商的 OpenAI 兼容 **Chat Completions JSON mode**（`response_format: json_object`），不使用 DeepSeek 等可能未实现的 Responses-only 助手 API。
- Prompt 要求返回 JSON 对象；解析 JSON 后在本地对照既有 transport/领域 schema 整表校验。
- 解析请求以 `submitted_at` 与 `timezone` 作为自然语言时间的唯一参考锚点。原文未提日期或时间时，每条候选记录使用提交时刻；原文明示“昨天、前天、上周五”等相对日期或具体日期时，AI 应解析实际发生日期。只给日期、未给时刻时，沿用提交时刻在请求时区中的时分秒，避免虚构另一个时间精度。
- 候选记录必须沿用请求 `timezone`；`occurred_at` 必须是可解析的 ISO-8601 instant，且转换到该时区后的日历日期必须严格等于 `local_date`。客户端在整表入账前执行上下文校验，任一记录不一致则整次解析失败，不得用录入日期静默覆盖 AI 结果，也不得部分入账。
- 若提供商不支持 JSON mode 或返回非法 JSON/合同，按既有 retryable/terminal 分类显式失败。

#### 2.0.6 相对旧网关路径的净熵

- **删除/退役**：固定 Cloudflare AI gateway 生产路径、`services/ai-gateway` 工作区、仅依赖 `EXPO_PUBLIC_AI_GATEWAY_URL` 的移动端路径，以及相关网关部署文档。
- **保留并收窄**：`packages/contracts` 中的解析请求/响应 schema，用途改为「客户端组装的最小解析请求 + 对 provider 输出的本地校验」，不再表示 client↔gateway 部署合同。
- **净熵**：降低 — 单一 BYOK 生产路径取代「环境变量网关 + Worker + 密钥托管」双轨；不保留 legacy fallback。

### 2.0.7 语音输入（预输入适配器）

一期语音识别**只**是记录页的预输入适配器：把口语转成原始自然语言文本，再进入既有「受控原文 → 用户点记下来 → 原子保存原文与唯一待解析作业 → AI 提案 → 本地整表校验 → 状态机入账」路径。

#### 分层与正式真相

| 层                 | 职责                           | 是否正式真相               |
| ------------------ | ------------------------------ | -------------------------- |
| SQLite 账本 / 作业 | 用户确认提交后的原文与解析作业 | **是** — 唯一账本事实源    |
| 应用状态机         | 提交原子性、整表校验、入账     | **是** — 唯一可入账路径    |
| 麦克风 PCM 流      | 用户控制的前台瞬时音频采集     | **否** — 不落盘、不入账本  |
| 本地语音模型       | 对 VAD 语段的转写提案          | **否** — 仅产生可编辑原文  |
| 模型文件与清单     | 可删除的设备端运行资源         | **否** — 不是账本事实      |
| 语音会话 UI 状态   | 权限、收音、增量预览、错误恢复 | **否** — 瞬时，不入 SQLite |

#### 产品合同

- **预输入**：识别结果写入记录页已有受控原文输入框；不新增语音账本实体、音频 blob、录音文件表或第二套全局状态存储。
- **不自动提交**：识别结束或得到最终转写后**不得**自动调用保存/创建解析作业；用户仍须点「记下来」。
- **单一模拟流式会话**：按住麦克风后启动 16 kHz 单声道 PCM 采集与 Silero VAD；音频块按顺序进入同一个 VAD。VAD 在停顿后产出完整语段，SenseVoice 对语段做离线识别并更新稳定预览；VAD 分段不替用户结束会话，松手才停止采集、冲刷 VAD 尾段并取得最终合并结果。
- **无录音文件**：语音只以进程内 PCM 块流过原生采集器和识别器，不生成 M4A、WAV 或其他临时录音文件，不进入 SQLite、导出、日志、崩溃附件或账本备份。
- **设备端识别**：固定使用 sherpa-onnx + `sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17` 的 INT8 模型与官方 `silero_vad.onnx`；SenseVoice 使用自动语言识别、ITN、16 kHz 单声道、CPU provider，支持中、英、日、韩、粤语及中文标点。模型就绪后，识别不使用网络，也不调用 Android/iOS 系统语音识别服务。
- **首次模型下载**：模型不随安装包分发。用户首次使用语音时，先展示约 240 MB、仅在本机运行、可删除后重下的说明和下载源选择；用户明确开始下载并校验完成后才能录音。
- **国内 / 境外下载源**：同一锁定模型提供「国内」与「境外」两个可见来源。不得按 IP、系统地区或请求失败静默切源；失败后由用户重试或显式改选来源。两源的每个文件必须匹配清单中锁定的字节数与 SHA-256，校验失败删除临时文件并拒绝加载。
- **模型文件生命周期**：下载写入独立临时路径，所有文件校验通过后以 ready 标记一次性发布。中断、空间不足、校验失败和应用重启均不得把半成品视为可用模型；用户可删除已下载模型，删除不影响任何账目、原文或 AI 配置。
- **识别引擎预热**：模型文件 ready 只表示校验后的文件可用，不等于 SenseVoice 已加载进内存。App 进入 active 且首屏完成后，应在不阻塞页面打开的前提下异步预热同一个进程级 SenseVoice 引擎；预热不得请求麦克风权限、启动 PCM 采集或创建账本数据。用户按住时若预热仍在进行，录音启动必须等待并复用同一个在途任务，不得并发加载第二份引擎。首次按住不应承担原本可以在打开 App 后提前完成的模型冷加载。
- **运行时所有权**：识别引擎由 App 级语音运行时持有，记录页只拥有当前按住会话。页面卸载或 App 进入后台必须取消当前 PCM / VAD 会话，但不得仅因切换页面重复销毁已预热引擎；进程结束后下次启动重新预热。删除离线模型时必须先释放识别引擎，再删除模型文件。
- **无云 ASR 产品路径**：不引入第三方云语音 API、不实现 provider fallback、不把完整账本或密钥交给语音服务。
- **无隐藏兜底**：模型未下载、下载失败、空间不足、校验失败、权限拒绝、无语音、忙、打断与原生错误必须呈现可恢复的中文 UI 状态；禁止回退到系统语音服务、静默吞错或伪装成已保存。
- **编辑语义**：收音中禁用直接编辑输入框；已完成语段只作为稳定预览，不能逐段追加到正式输入。当前未停顿的语段可以到停顿或松手时才出现。松手并完成冲刷后，至多一次把按顺序合并的最终结果追加到录音前已有文本。失败或取消保留录音前已有键入文本，不得把中间或空结果写入正式输入。
- **按住说话**：默认手势为按下麦克风开始、松开结束；短暂停顿、系统识别连接状态或厂商服务超时不得结束录音。手指移出按钮后松开仍按正常结束处理，不把已录内容静默丢弃。录音和转写中忽略额外按压事件。
- **首次授权边界**：若系统权限弹窗打断本次按住手势，授权完成后不得在用户已经松手的情况下偷偷开始录音；回到空闲态并提示「权限已开启，请再按住说话」。权限拒绝仍进入明确可恢复错误。
- **无障碍等价操作**：屏幕阅读器启用时，麦克风按钮改用点按切换开始/结束，提供与按住/松开相同的录音—转写合同。无障碍等价入口不是第二套录音实现。
- **用户控制结束**：正常录音只由用户松手结束。App 进入后台属于明确的生命周期中断，应取消本次录音而不是后台持续采集。
- **非视觉反馈**：真正开始收音时提供一次短震动，用户主动停止并进入转写时提供一次双震动，错误或中断时提供另一种可区分的震动；该反馈不取代屏幕状态与无障碍标签，也不播放可能被麦克风录进去的提示音。
- **生命周期**：页面卸载或 App 进入后台时停止 PCM 采集、取消识别流并取消订阅；语音状态仅为瞬时 UI/应用状态。识别引擎与单次采集会话分属 App 级运行时和页面会话，不能把页面卸载误当成整个引擎运行时销毁。

#### 真机验证边界

- 模拟器可验证麦克风控件、模型下载状态、权限文案/流程与部分不可用/取消路径，**不能**等价于真机中文识别质量验收。
- 一期识别质量与可用性以**实体 iPhone 与 Android** 验收为准；模拟器限制必须显式记为边界，不得用假通过掩盖。

#### 相对无语音路径的净熵

- **删除**：Android/iOS 系统语音识别适配器及其权限、厂商服务发现、网络超时和兼容分支。
- **删除**：录音文件、M4A → WAV 转换、录后批量推理和旧模型运行路径；模型管理器只保留一次性的旧缓存 ID 清理，不保留兼容加载或识别 fallback。
- **新增并收窄**：一个锁定版本的 SenseVoice + Silero VAD 模型清单、显式双下载源、校验与可删除缓存，以及当前 RN SDK 缺失的薄 VAD 原生桥；它们只替代旧语音预输入基础设施，不进入账本领域。
- **不新增**：音频账本实体、后台录音、第三方云 ASR、provider fallback、自动提交、账本双轨。
- **净熵**：下降 — 官方 VAD 分段 + 单一离线识别器替代 Zipformer online recognizer，PCM 仍不落盘；两源只传输同一校验内容，不形成两套识别语义，也不保留模型 fallback。

### 2.1 手工纠错

第一期以直接编辑结构化字段作为主要纠错入口，不实现通过追加自然语言指令修改上一笔账目的对话式纠错。

- 用户可以直接修改单条消费记录的商品原价、本次实付、优惠券抵扣、时间以及各类统计维度。收支方向作为内部账本与导出字段保留，不在记录详情中直接展示或编辑；编辑其他字段不得改写原方向。
- 用户保存修改前，客户端必须执行与自动入账相同的本地合同校验；金额关系不成立时应明确指出问题，不能静默补齐。
- 用户保存后的结构化结果是该记录当前有效的正式结果，优先级高于 AI 解析结果。
- 后台任务重试、模型升级或重新解析不得静默覆盖用户手工修改。
- 若用户主动要求重新解析，新的结果必须先供用户比较和确认，不能直接替换手工结果。
- 原始输入保持不变；修改结构化字段不等于篡改用户最初记录的文字。
- 第一期只需保存原始输入与当前有效结构化结果，不要求实现完整的字段修改版本历史。

### 2.2 模式与默认标签

用户可以创建多个记账模式，但同一时间最多只能开启一个。模式由名称和一组带类型的默认标签组成，例如：

- 模式：江西旅游
- 默认标签：行程 / 江西旅游、地点 / 景德镇

模式只负责提供可见的默认标签，不代表隐藏的自动分类规则：

- 模式开启后，新记录的录入界面默认展示该模式提供的标签。
- 开启另一个模式时，当前模式自动关闭；用户也可以不启用任何模式。
- 录入界面提供“本笔跳出模式”的快捷操作，一次关闭当前记录的全部模式默认标签，但不关闭模式本身。
- 用户可以在提交某条记录前关闭其中一个或多个默认标签；该操作只影响当前记录，不修改模式本身。
- 用户提交后仍可以从该记录中手工清除或修改这些标签。
- 保存原始输入时，同时保存本次实际采用的默认标签快照及其来源模式。解析生成多条消费记录时，这些记录分别继承该快照，用户之后可以逐条修改。
- 保存原始输入时，同时保存本次是否纳入当前模式统计；未使用“本笔跳出模式”时，解析生成的消费记录默认分别纳入，使用后均不纳入。
- 模式来源只用于追溯提交时开启了什么模式；模式统计归属是独立的当前有效状态。用户可以在入账后把记录移入或移出该模式，不能仅凭历史来源强行纳入统计。
- 之后修改、切换或关闭模式，不能追溯修改已经保存的历史记录。
- 模式标签在提交时即可本地写入，不需要等待 AI；AI 可以继续补充从原文识别出的其他标签。
- AI 和后台任务不能静默恢复用户在提交前关闭或提交后清除的模式标签。

模式表达的是“当前一段时间内，大部分记录通常带有这些标签”。少数例外通过“本笔跳出模式”处理，不需要用户为了单笔例外关闭模式、提交后再重新开启。

标签管理支持重命名、合并与删除。删除采用软删除：只有未被有效消费记录或模式默认标签引用的标签可以直接删除，删除时同时移出统计分组；仍有引用时必须明确阻止，并提示用户先合并标签或移除模式引用，不能让历史账目丢失标签语义。

### 2.3 提交与后台解析状态机

用户提交一次自然语言原始输入时，本地必须在同一次原子操作中：

1. 保存原始输入及提交时生效的上下文。
2. 创建与该原始输入唯一关联的待解析作业。

上述本地操作完成后立即向用户显示“已记录”，不得等待网络请求或 AI 返回。解析作业由本地持久化后台队列执行；App 被关闭或系统中断后，待处理状态不能丢失。同一作业重复执行不得生成重复账目。

原始输入在解析生命周期中至少区分以下可见状态：

- 待解析：原文已安全保存，尚未获得结构化结果。
- 已入账：解析生成的一条或多条扁平消费记录已生效并进入本地统计。
- 待确认：结构化结果已生成，但尚未进入正式统计。
- 解析失败：原文仍然存在，展示明确错误，并允许用户主动重试或手工整理。

“已撤销”是从原始输入及其当前有效消费记录派生出的可见状态，不是解析失败：当一次已入账输入生成的消费记录已全部撤销时，账单应显示“已撤销”，不得把仍为 `posted` 的原始输入投影成“解析失败”。

后台队列不得用静默默认值、吞错或未经约定的兼容解析把失败记录伪装成已入账。

### 2.4 解析确认模式

系统提供一个全局设置：

- 默认模式——直接入账：AI 返回结果通过本地合同校验后，自动成为当前结构化结果并进入统计。用户可以事后查看、修改或撤销。
- 可选模式——入账前确认：AI 返回结果先进入“待确认”，只有用户确认后才进入正式统计；用户可以在确认前修改或拒绝结果。

一次原始输入生成多条消费记录时，AI 返回的是本次解析的扁平记录列表。默认模式下，整个列表通过本地合同校验后才分别入账；任一候选记录不合法时，不允许只把其余记录静默部分入账。确认模式下，确认页可以一次展示并修改该列表；确认后生成的消费记录立即彼此独立，不能持久化为购物记录组。

两种模式都必须先保存原文并在后台解析，不能用确认页阻塞用户继续记录。每次原始输入应保存提交时采用的确认模式，避免用户修改全局设置后改变既有待处理输入的行为。

AI 输出始终视为不可信输入，必须经过本地结构、金额关系和引用完整性校验。未通过校验的结果进入“解析失败”，不能自动入账。

## 3. 正式真相与派生信息

### 3.1 事实记录

以下信息属于账本事实：

- 用户原始输入。
- 用户明确设置或变更的持续上下文。
- 用户确认后的资金流与消费事件。

### 3.2 原始输入与消费记录

- 原始输入保存用户提交的完整自然语言、提交时间、当时采用的模式与默认标签快照，以及解析生命周期状态。
- 消费记录是正式账本的最小业务单位；一条消费记录只表达一笔消费，并独立拥有商品原价、本次实付、优惠券抵扣、发生时间、商户、标签和模式归属。
- 原始输入的 `submitted_at` 表示用户何时记下这句话；消费记录的 `occurred_at + timezone + local_date` 表示消费实际何时发生。二者不得因 UI 合并展示而混为同一个时间。
- 一次原始输入可以生成零条、一条或多条并列消费记录。解析失败或待确认时可以暂时没有正式消费记录。
- 多条消费记录可以引用同一个原始输入以便追溯，但彼此之间不存在父子明细关系，也不存在需要单独维护的“购物记录组”。
- 对其中一条消费记录的编辑、撤销或标签调整不应隐式修改同一原始输入生成的其他消费记录。
- 同一原始输入生成多条消费记录时，界面可以让它们在时间线上相邻显示，但这种视觉邻近不是新的业务实体。
- 同一原始输入生成多条消费记录时，每条记录保存从零开始的稳定来源序号；该序号只用于复现原句中的并列顺序，不创建父子关系或购物组。列表在发生时间相同的情况下必须按该序号稳定展示。

### 3.3 结构化结果

系统从事实记录中提取或计算：

- 收入、支出等资金变化。
- 一条或多条扁平消费记录。
- 商品原价、本次实付和优惠券抵扣。
- 商户、类目、渠道、地点、行程、人物和用途等带类型维度。

结构化结果允许用户逐条修正；统计结果是消费记录的派生视图，不是独立事实源。

## 4. 核心用例

### 4.0 账单、待处理与分析

- 全局一级入口使用「账单」，不再保留独立「今日账」页面或「看账本」双轨。记录页的查看入口与底部导航均进入同一个账单页；“今天”只是账单中的日期分组。
- 账单页顶部先展示全部未完成原始输入，包括待解析、待确认和解析失败，不受录入日期限制；内部按 `submitted_at` 倒序。它们仍是原始输入状态，不是消费记录，不进入金额合计和统计。
- 待处理区之后展示全部当前有效消费记录，按实际发生 `local_date` 倒序分组，同一天按 `occurred_at` 倒序；同一原始输入生成且发生时刻相同的平级记录继续按 `source_sequence` 正序，复现原句顺序。
- 已完成且仍有有效消费记录的原始输入不在待处理区重复展示；一次输入生成多笔消费时，账单直接展示多条平级消费记录。
- 已入账记录全部被撤销后，原始输入在账单中投影为“已撤销”，不进入待处理数量、金额合计或统计。
- 账单页提供本月消费概览与「消费占比 / 消费趋势」分析入口，不把统计查询参数直接铺成首页表单。
- 消费占比支持选择时间范围或单个模式范围；选择模式时默认统计该模式的全部历史记录，只有用户主动限定时间时才叠加日期条件。
- 消费趋势一期按时间范围查看，可选标签筛选；界面不得让用户误以为模式筛选会作用于趋势后再静默忽略。
- 模式、标签与时间是彼此可辨认的筛选维度。没有模式时应说明并提供创建入口，不能只留下一个含义不明的「时间范围」标签。
- 结果页必须用自然语言展示当前条件。占比桶点入记录列表时，列表必须严格对应所点的桶；「未归类」只展示不含该互斥统计组任一标签的记录。
- 「下钻、互斥组、统计口径」等内部分析术语不作为普通用户操作文案；分别使用「查看这些记录、按什么分类、消费金额」等用户语言。
- 账单中的已入账记录支持长按删除并二次确认；轻点仍进入详情。列表不常驻高强调度的删除图标，进入详情也不是删除记录的唯一入口。

#### 4.0.1 自然语言日期

- “买菜花了 30 元”未提供发生日期，记录发生时刻等于本次原始输入提交时刻。
- “昨天买菜花了 30 元”以提交时区计算昨天，记录进入昨天的账单分组与统计时间桶。
- “前天打车 26 元”“上周五午饭 35 元”和明确年月日遵循同一参考锚点；不能以 AI 请求执行时刻或响应完成时刻计算。
- 一次输入中的多条消费可以各自带不同日期；每条记录独立解析和保存自己的发生时间，但候选列表仍整体验证、整体生效。

### 4.1 继承旅行上下文

已知当前上下文：

- 行程：江西旅游
- 地点：景德镇

用户输入：

> 在家乡菜吃午饭花了100元

期望记录：

- 支出：100 元
- 商户：家乡菜
- 类目：餐饮
- 用途：午餐
- 行程：江西旅游
- 地点：景德镇
- 原始输入：完整保留

用户不需要在每条记录中重复输入当前行程和地点。用户通过开启“江西旅游”模式获得默认标签；地点或行程发生变化时，可以修改模式的默认标签或关闭模式。某条记录不适用某个默认标签时，可以在提交前关闭，或在入账后手工清除。

### 4.2 消费时使用优惠券

一期不管理优惠券资产，不要求用户记录买券，也不建立或匹配优惠券 ID。用户只需在记录消费时描述本次账单使用优惠券抵扣了多少钱。

- “买菜实付 300 元，优惠券抵扣 20 元”：本次实付 300 元，优惠券抵扣 20 元，商品原价 320 元。
- “买菜原价 300 元，优惠券抵扣 20 元”：商品原价 300 元，优惠券抵扣 20 元，本次实付 280 元。
- “花了 / 付了 / 实付”默认表达本次实付；“原价 / 账单金额”表达优惠前商品原价。
- 金额关系固定为：商品原价 = 本次实付 + 优惠券抵扣。
- 原文没有说明优惠券抵扣时，抵扣为 0，商品原价等于本次实付。
- AI 输出和手工编辑均不得包含优惠券 ID、买券记录、券成本、券面值、券余额或券状态。

### 4.3 一次输入生成多条消费记录

用户输入：

> 买xx花了100，买yy花了200，买zz花了20

期望记录：

- 生成三条并列消费记录：xx 100 元、yy 200 元、zz 20 元。
- 不生成购物记录组，也不在任何一条记录下创建子明细。
- 三条消费记录可以分别继承同一个原始输入中的时间、渠道和模式默认标签，但继承后都是可独立修改的正式字段。
- 三条记录都引用同一个原始输入，便于追溯当时写下的完整文字。
- 账页与统计直接按三条消费记录处理；如需显示合计 320 元，应实时求和，不保存一条额外的“合计消费记录”。
- 用户可以独立编辑或撤销其中一条记录，不影响另外两条。

### 4.4 连续快速记录

用户连续提交多条自然语言记录时：

- 每次提交只等待本地保存成功，不等待 AI。
- 用户提交上一条后可以立即输入下一条。
- 每次原始输入独立显示待解析、已入账、待确认或解析失败状态；解析完成后展示由它生成的扁平消费记录。
- 后台返回顺序与提交顺序不同时，结果仍必须关联到各自的原始输入，不能串账。
- 默认模式下，合法解析结果自动进入统计；开启“入账前确认”后，解析结果逐条等待用户确认。

### 4.5 修正自动入账结果

已自动入账的记录被 AI 错误解析时：

- 用户打开该记录并直接编辑错误字段。
- 保存成功后，本地统计立即以修改后的结果重新计算。
- 原始输入继续展示，便于用户对照。
- 旧的 AI 结果不再生效，后续后台作业不能把它恢复回来。

## 5. 分类与统计维度

用户记录时不必理解或维护固定的分类层级。系统底层使用带类型的统计维度，例如：

- 类目
- 行程
- 地点
- 商户
- 渠道
- 人物
- 用途

界面可以提供类似标签的轻量交互，但不能把所有维度存成无类型、无约束的扁平字符串；同义词归并和维度修改不得破坏原始输入。

这些类型是底层语义，不是固定的一级导航或要求用户逐项填写的分类栏。不同类型的标签可以同时附着在同一笔消费上，因此任意标签集合天然可能重叠，不能直接把所有标签金额相加后计算占比。

### 5.1 标签创建与归一

本地带类型的标签库是标签身份与归并关系的正式真相。AI 只负责在单次解析中提出匹配或创建建议。

- 调用 AI 解析时，向模型提供本地已经使用的相关标签，包括标签名称、类型和已确认别名。
- AI 有足够信心时，可以让新记录引用已有标签。
- AI 不确定时必须创建新标签，不能为了减少标签数量而强行映射到语义相近的已有标签。
- 客户端不得再用模糊字符串替换或隐藏规则二次强制归一 AI 的结果。
- AI 创建的新标签立即成为本地标签库中的正式标签，并可被后续解析复用。
- 用户可以重命名标签或把重复标签合并到一个目标标签。
- 合并后，已有账目统一引用目标标签并重新计算统计；来源标签保留合并指向，不能留下两套同时生效的统计身份。
- 标签的创建、匹配、重命名或合并都不能修改原始日记文本。

标签归一失败的可接受结果是暂时存在两个标签；不可接受的结果是把语义不同的记录静默合并，导致历史统计失真。

### 5.2 标签的筛选与分组能力

- 所有有效标签都可以作为筛选条件。
- 只有被定义为“互斥统计组”的标签集合可以作为消费占比分组，例如同一层级的消费类目或互斥地点归属。
- 一期内置的“消费类目”互斥统计组以当前有效、未合并且类型为 `category` 的标签集合为正式成员；标签从任何入口创建或改变类型时，SQLite 必须在同一写入边界维护该成员关系，不能等到查询统计时临时补齐。
- 同一消费记录在一个互斥统计组内最多归入一个有效标签；没有匹配标签时归入该组的“未归类”桶。
- 不属于互斥统计组的自由标签仍可用于筛选和查看独立金额，但不能伪装成不重不漏的占比分桶。
- 底层类型与互斥统计组可以帮助系统计算，但界面不得因此恢复固定的“行程 / 地点 / 类目 / 商户 / 渠道 / 用途”一级 Tab。

### 5.3 一期预置标签

首次建库和已有账本升级时，幂等补齐以下常用标签；同类型同名的有效标签已经存在时不得重复创建，也不得覆盖用户已有名称、别名或引用：

- 消费类目：餐饮、买菜、购物、娱乐、旅游、交通、住宿、医疗健康、居住缴费、通讯网络、生活服务、教育学习、人情往来、宠物、其他。
- 不预置含义空泛的通用行程标签；行程标签应表达具体上下文，例如“江西旅游”“港澳旅行”，通常由模式或自然语言产生。

“旅游”描述旅游相关消费的消费类目，属于“消费类目”互斥统计组；具体行程则由“江西旅游”等行程标签表达。一笔旅游中的普通午餐仍应以“餐饮”参与消费类目占比，同时可带“江西旅游”用于筛选；办理旅游证件等整体旅行支出可归入“旅游”类目。已有账本升级时，旧版预置的通用“旅游”行程标签必须原地收敛为“旅游”消费类目，保留稳定 ID、历史账目和模式引用，并立即进入消费类目占比。未被账目或模式引用的预置标签与用户新建标签遵循相同删除规则，不设不可删除的系统标签特权。

## 6. 统计查询合同

### 6.1 共同口径

- 统计的最小计量粒度是当前有效的扁平消费记录；不存在记录下的子明细统计路径。
- “消费”默认指本次实付，不指商品原价。未来若允许切换口径，查询结果必须明确标出当前口径，禁止在同一结果中混用。
- 只统计已经入账且当前有效的消费记录；待解析、待确认、解析失败的原始输入，以及已撤销消费记录不进入正式统计。
- 时间条件按账目实际发生时间计算，不按原文创建时间或 AI 解析完成时间计算。
- 标签只参与筛选或分桶，不复制消费记录；无论一条记录带有多少标签，其金额在同一统计结果中都不能被重复累加。
- 每个统计结果必须能下钻到构成该结果的消费记录，并继续追溯到原始输入。
- 统计查询统一按以下顺序执行：确定时间或模式范围，应用可选标签筛选，再按互斥统计组分桶或按时间聚合。后续步骤不能绕过前一步重新引入已被排除的消费记录。
- 所有支持多个标签的筛选都必须显式携带“同时满足”或“满足任一”语义。“同时满足”只保留拥有全部所选标签的消费记录；“满足任一”对消费记录集合取并集，同一记录命中多个标签时仍只保留一次。

### 6.2 时间范围内的消费占比

用户选择时间范围和一个互斥统计组，并可选一个或多个标签作为筛选条件；系统先筛选消费记录，再计算所选统计组内各标签的消费金额与占比。

必须满足：

- 分母等于时间范围内通过可选标签筛选后的全部本次实付；没有标签筛选时，等于该时间范围内的全部本次实付。
- 每条消费记录在所选统计组内恰好进入一个桶；没有标签时进入“未归类”。
- 各桶金额之和必须等于分母，既不重复也不遗漏。
- 任意跨类型、会重叠的标签集合不能生成占比图；系统应改为展示可重叠的独立金额，或要求用户选择一个互斥统计组。

例如，一笔 100 元午餐同时带有“江西旅游、景德镇、餐饮、午餐”。按消费类目统计时只进入“餐饮”桶一次；按地点统计时只进入“景德镇”桶一次；不能把这四个标签并列后声称总占比为 100%。

### 6.3 模式范围内的消费占比

用户选择一个模式和一个互斥统计组，并可选一个或多个标签作为筛选条件；系统先取得明确纳入该模式的消费记录，再应用标签筛选，最后计算所选统计组内各标签消费金额与占比。

- 模式范围以记录当前有效的模式统计归属为准，不以“提交时曾开启该模式”或标签名称猜测。
- 使用“本笔跳出模式”的记录默认不进入该模式统计。
- 之后手工移入或移出模式时，统计结果立即重新计算。
- 模式范围也可以叠加时间条件，但未指定时间时覆盖该模式下全部有效记录。
- 分桶继续遵守恰好一次与“未归类”规则，各桶金额之和必须等于模式范围内通过可选标签筛选后的消费总额。

### 6.4 消费趋势

用户选择时间范围，并可选一个或多个标签作为筛选条件，系统按时间桶展示本次实付趋势。

- 多个标签筛选使用共同口径中定义的“同时满足”或“满足任一”语义；界面可以提供默认值，但不能用隐藏规则解释。
- 趋势按账目实际发生时间落入日、周或月时间桶；当前粒度必须可见。
- 范围内没有消费的时间桶显示为零，不能跳过后让趋势线产生错误连续性。
- 每个时间桶的金额等于其中符合筛选条件的有效消费记录之和，并可以下钻查看记录。

### 6.5 验收不变量

对任意占比统计：

```text
所有分桶金额之和 = 当前统计范围内的本次实付总额
每条有效消费记录在所选互斥统计组内恰好计入一次
```

对任意趋势统计：

```text
所有时间桶金额之和 = 相同范围和筛选条件下的本次实付总额
同一消费记录在同一结果中最多计入一次
```

## 7. 当前未决问题

- 除合同校验失败外，是否还需要按金额歧义或解析置信度把默认模式下的个别记录升级为“待确认”。
- 本地账本未来如何备份、恢复和迁移，避免换机造成数据丢失；Excel 分析导出不承担该职责。
- 后续跨设备同步通过何种可信介质完成，以及如何继续满足个人数据边界。
- 家庭纳入状态默认是“仅个人”还是“家庭可见”，以及用户如何批量设置和修正规则。
- 家庭成员能看到纳入记录的完整明细，还是只能看到汇总结果。
- 提供给 AI 的已有标签数量过多时，如何选取相关候选，同时避免遗漏本应归一的标签。
- 原文明示的标签与模式默认标签冲突时，是自动替换默认值还是同时保留并提示用户。
- 第一期开放哪些互斥统计组，以及用户如何修正某条消费记录在统计组中的归属。

## 8. Excel 分析导出

### 8.1 目标

导出的 `.xlsx` 文件应便于 Excel、表格软件、数据分析工具和人工审阅直接使用。导出在本地生成，不需要把账本上传到在线服务。

同一个导出入口支持：

- 自定义导出：选择开始时间、结束时间和需要导出的业务字段。
- 完整账本：自动选择全部时间和全部账本业务字段。

时间筛选默认按账目的实际发生时间执行，而不是记录创建时间或 AI 完成解析的时间。所有本地账本业务字段都必须出现在字段选择器中；App 凭据、AI 服务密钥和后台队列内部状态不属于账本业务字段，不得导出。

### 8.2 工作簿结构

工作簿至少包含以下数据表；各表通过稳定 ID 关联：

- `原始输入`：每行一次用户提交，包含原始输入 ID、完整原文、提交时间、解析状态、确认模式和当时的模式快照。
- `消费记录`：每行一条扁平消费记录，包含消费记录 ID、来源原始输入 ID、发生时间、收支方向、商品原价、本次实付、优惠券抵扣、商户和渠道等可直接分析的字段。不存在子明细行。
- `消费记录标签`：每行表示一条消费记录与一个带类型标签的关联，支持一条记录拥有多个标签，并标明标签来自 AI、手工编辑还是模式默认值。
- `标签`：标签 ID、类型、当前名称、别名和合并指向，便于外部工具理解标签归一关系。
- `模式`：模式 ID、名称和当前配置；历史记录实际采用的模式标签以记录快照为准。

如果一期某类数据尚未产生，对应数据表仍保留表头，便于其他软件稳定读取。

自定义导出只输出用户选择的业务字段及维持所选数据关联所必需的稳定 ID。完整账本导出包含上述各表的全部业务字段；待解析、待确认和解析失败的原始输入也必须包含，不能只导出已经生成消费记录并进入统计的数据。

### 8.3 可分析性约束

- 第一行是稳定列名，不使用合并单元格或依赖视觉位置表达数据关系。
- 金额列必须是可计算的数值，币种单独成列，不能导出为“100元”这类文本。
- 时间包含明确时区，并使用可被通用工具识别的格式。
- 一行只表达一种粒度；原始输入、消费记录和标签关系不能混成含义不稳定的一行。
- 保留原始输入，同时导出当前有效的结构化结果。
- 用户手工修正后的结果作为当前值导出，已失效的 AI 解析结果不参与分析导出。
- 导出范围和生成时间写入独立的说明表，不能依赖文件名猜测。
- 工作簿写明数据格式版本，便于未来版本继续识别字段含义。
